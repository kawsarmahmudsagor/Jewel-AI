## COORDINATE SYSTEM — for context if you touch any position
════════════════════════════════════════════════════════
- Ring center at origin (0,0,0). +Z is up. The finger-hole axis runs horizontally (along Y)
  because the band is built with rotate([90,0,0]) rotate_extrude(...).
- band_apex_z = ring_inner_radius + band_tube_radius is the world-Z seat the head sits on.
- Every head Z coordinate (gallery_top_z, stone_girdle_z, stone_table_z, prong_tip_z) is
  derived as band_apex_z + (stackValue - bandTopZ) — never a raw stack number, never a magic
  number. These are already declared as variables at the top of the draft; reuse them.
- All units mm.

## OPENSCAD GOTCHAS — still apply if you rewrite code
════════════════════════════════════════════════════════
1. Variables are immutable — one value per scope. Never reassign or concat-accumulate
   (`points = concat(points, ...)` in a loop is illegal). Build lists with one list
   comprehension, or bake literal coordinate arrays as the draft does.
2. No floating/disconnected parts — every module must overlap its parent so union() fuses
   into one solid (sink feet below band_apex_z, embed prong bases below stone_girdle_z).
3. Keep $fn ≤ 96 globally; small $fn (16–48) inside hull()/loops is fine.
4. Prong tip radial offset must stay LESS than gem_table_radius — tips curl in over the table
   edge, they never stand outside the stone's silhouette like spikes.
5. The finger hole already exists from the band profile's inner wall via rotate_extrude — do
   not add a difference() cut along the wrong axis.

## WHAT TO COMPARE AGAINST THE REFERENCE PHOTO
════════════════════════════════════════════════════════
You have MULTIPLE rendered angles. Use them differently:
- The angle MATCHING the reference photo is your primary, direct comparison — silhouette,
  proportions, and framing should line up with the photo closely here.
- The other angles (top/front/left) have no equivalent in the photo — don't expect them to
  "match" anything. Their job is to expose defects that are invisible from a single angle: a
  stone that's actually sunken into the band only shows up from the side; pavé floating
  disconnected from the band shows up clearly from the top. Check every angle for structural
  soundness even though only one of them is being compared against the photo directly.

Judge against the PHOTO (via the matching angle) on:
- Overall silhouette: band profile/width, shoulder rise, gallery height and openness
- Stone shape and proportion relative to the band (size ratio, length/width ratio)
- Prong count, visibility, and whether they read as claws gripping the crown (not spikes
  floating above it, not stubs buried in the gallery)
- Gallery/setting style (basket vs cathedral vs trellis vs bezel) matching what's visible
- Relative metal/stone color intent (exact rendering color is not meaningful — see below)
- Any side stones / pavé that should be present but are missing, or vice versa

EXPLICITLY IGNORE when judging any render:
- OpenSCAD's flat CGAL preview shading vs the photo's real lighting/reflections/specular
  highlights — this is a rendering-engine difference, not a geometry defect
- Background, hand, or any non-ring content in the photo
- Minor anti-aliasing/jagged edges from the preview renderer (the top/front/left views use a
  faster preview mode, so they're rougher-looking than the matching-angle render — that
  roughness itself is not a defect)

## MANDATORY CHECKLIST — answer honestly, item by item, before setting status
════════════════════════════════════════════════════════
A single overall "looks fine" judgment is exactly how broken renders have slipped through
before (floating pavé stones, an oversized halo cup, spike-shaped prongs were all once accepted
as "final" on round 1). Instead of one holistic call, answer each of these as true/false by
actually checking the render against the photo:

- band_style_matches: band configuration, cross-section, and shoulder style match the photo
- stone_shape_count_matches: center stone shape/proportions AND any side-stone count match
- prong_count_and_style_matches: prong count matches, and prongs read as claws gripping the
  crown — not spikes above it, not stubs buried in the gallery
- decorative_features_match: halo / pavé / milgrain / channel / filigree are present in the
  render wherever the photo shows them, absent wherever it doesn't, and actually VISIBLE
  (not buried inside the band or floating disconnected from it)
- no_floating_or_buried_geometry: every visible part sits ON the band/gallery surface with no
  gaps and no parts swallowed inside the metal — check this across ALL provided angles, not
  just the one matching the photo; this is exactly the kind of defect a single angle can hide

status may only be "final" if every single item above is true. If even one is false, status
MUST be "revise" — fix that specific issue in scad_code rather than re-submitting the same file.
